What caused the three failures?

No test-bench startup or adapter error was found to explain these three cases.

The first two failed because the selected native computer-use runtime delivered input that Illustrator did not reliably interpret as Pen drags or modifier shortcuts. One-variable drag control

Both controls use a normal-integrity Python process, identical window/screenshot mapping and the same four mouse records: move to start, button down, one move to the endpoint, button up. Only the spacing between those records changes. The screenshots below are unchanged exports of those diagnostic paths, not repaired benchmark drawings.

What the Windows event trace shows

A short-lived observer recorded only injected mouse events and the specific injected modifier/tool keys while the diagnostic Illustrator window was foreground. The native runtime emitted one move while the mouse button was held; observed button-down to button-up spans were about 15–32 ms. Shift-down, C-down, C-up and Shift-up shared a timestamp. This is not a reversed key order or an unsupported chord spelling: Shift_L+c is explicitly documented.

The event trace also confirms the screenshot-to-screen transform: native screenshot point (692,736) reached approximately (1380,1476) on the 3866×2186 physical window. Anchors land where expected; the symptom is the missing handles, not a whole-window 2× coordinate error. The broad ACU positive control used an approximate 2× mapping; the later normal-process control used the full observed window mapping and isolates spacing.

For keys, a normal-process, scanless Shift+C batch selected Scissors, matching the vendor result. Spacing the same key records by 40 ms selected Anchor Point. UI Access input succeeded even without spacing, so “all zero-delay input is broken” would be too broad. These controls establish sensitivity to delivery conditions, not a proven line-level defect in the closed native helper. A further 15 ms normal-process mouse control also retained 3/3 handles, with coarse event timings overlapping the native trace. Therefore duration alone is not a complete explanation. The fault is localized to unreliable native-runtime delivery to Illustrator; the exact internal mechanism remains unproven.

The successful third native trial does not disprove the defect: it encountered missing handles too and repaired seven anchors with ordinary GUI smoothing and handle drags. The first two actors stopped rather than finding that recovery. Their unsuccessful arm results remain valid because the benchmark compares the agent and its assigned runtime together.

CUA screenshot overwrite: reproduced safely

The actor launched in the correct workspace. Its first explicit relative capture already returned a home-directory path, before its later cd ~. Changing the client shell directory therefore did not control the daemon’s output directory.

For the live reproduction I created a uniquely named, diagnostic-owned sentinel in home and a different sentinel of the same name in the caller’s scratch directory. A screenshot request using the relative filename replaced the home sentinel with a PNG while leaving the caller-directory sentinel untouched. An absolute scratch path wrote the expected PNG and preserved the home sentinel. Both test files were ours; the real cp.png was not touched.

  • Relative output overwrote the pre-existing test sentinel: reproduced.
  • Absolute run-scoped output preserved it: verified.
  • The frozen CUA workflow already said “Use an absolute, run-scoped output path.” The actor read the main skill and part of the Windows guide, but no WORKFLOW read was captured.
  • The actor also saw earlier home-directory outputs and a listing of the old cp.png before choosing that name. This supports an ownership mistake, not malicious intent.
  • The old file was used by the 15 October benchmark. It remained a pre-existing file for this fresh actor; prior benchmark origin did not grant permission to replace it.

What is and is not a bench defect

The actor cwd and shared-daemon restart matched the frozen policy. No no-clobber or caller-cwd promise was found for the screenshot API. Starting an actor in a different directory would not fix daemon-relative JSON paths; silently replacing the shared runtime with a run-owned daemon would change the benchmark profile.

The automatic audit has a real coverage gap: it fingerprints guarded source/documents and checks Write/Edit tool targets, but does not reliably attribute daemon-written screenshot files. The manual review caught this overwrite using the pre-round file inventory and recorded requests. That gap did not cause the write, and blanket failure on any home-file change would falsely blame unrelated applications. I have not added a location-only ban, a broad home-directory scan, or a speculative daemon-cwd patch.

The correct classification remains a manually reviewed ownership violation, separate from its passing drawing. The independent review’s claim that a default capture created s.png was imprecise: the explicit relative screenshot_out_file request at event 135 establishes that write. This correction does not change the cp.png evidence.

Verified bench defect fixed: export dirty-flag false alarm

A diagnostic failed before drawing and left a saved blank document. Its native export report showed:

Before export: saved=true,  page_items=0, artwork_signature=4177446506
After export:  saved=false, page_items=0, artwork_signature=4177446506

The exporter compared the entire metadata object and reported “Drawing changed during maintainer export,” retaining the blank. The artwork had not changed: Illustrator had only marked the document dirty. The affected diagnostic’s original refusal and native PNG are preserved; a separate identity-checked recovery closed its verified blank later.

bench/illustrator_pen_export.py now permits only a post-export transition to saved:false. The first pre-export snapshot must match exactly. A retry may carry the same harmless dirty flag from the preceding export attempt; document path/name, artwork signature and every other recorded field must still match on every attempt. A change to geometry or appearance remains a terminal integrity refusal. An unexpected transition from dirty to saved is not allowed.

Limits, unchanged behavior and cleanup

  • The vendor’s Windows API has no supported drag duration or per-key hold-time option. I did not patch its installed package, invent unsupported arguments, switch transport/provider, coach benchmark actors or substitute ACU input in a scored native trial.
  • 15 ms and 40 ms are successful diagnostic controls, not universally proven timing thresholds. Occasional native drags do work; this is high-failure-rate degradation, not an absolute inability to make curves. The native implementation is closed at the inspected boundary; timing sensitivity is demonstrated, while its exact internal event-consumption mechanism remains unknown.
  • The tested runtime path and selected skill match the recorded configuration. Historical hashes of every installed native binary were not captured, so this is not a retroactive byte-for-byte attestation of all vendor internals.
  • No new benchmark trial, API-token comparison or replacement slot was added. Diagnostics have no model actor and are not pooled with the 15 original trials.
  • All diagnostic-owned documents and the task-started Illustrator process were closed. The input observers and MCP process trees were stopped; temporary home sentinels were removed. CUA sessions are empty, the benchmark lock is absent, and no fixed port or temporary server remains.
  • The original 15 PNG hashes still match. The real home cp.png remains byte-identical to its pre-diagnosis state. No original trial metric or verdict was edited.

A vendor-runtime fix or update can be evaluated with the retained minimal repro before scheduling a new, explicitly versioned comparison. Changing the benchmark setup to hide this runtime weakness would invalidate the comparison rather than fix the measured failure.
