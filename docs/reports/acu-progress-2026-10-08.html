The screenshot script, explained

Before it, ACU could act but not see. The launcher and prelude let an agent click, type, and drive windows, but the agent only knew what was on screen when it already knew the window by title or a control by name. For anything else it has to look.

The screenshot script is the way to look. It captures one display, one window, or one rectangle to a PNG file, then prints the image size, the screen rectangle it came from, and the scale between image pixels and screen pixels. The agent reads the PNG as an image, decides where to click, converts those image coordinates to screen coordinates with the printed origin and scale, and writes a script that clicks there. Built 2026-10-09 with the three actions chosen on 2026-10-08: fullscreen, app, and custom.

1. LookTake a screenshot, read it as an image
2. ActWrite a short script, run it through the launcher
3. CheckScreenshot again, or wait for the expected window

It is step 3 of the perception ladder from the brainstorm: named element first, element bounds second, screenshot third. Until the accessibility-tree binding arrives in milestone 2, it is the only perception step available, which is why it came before the skill file. A skill file that says "look, then act" needs a way to look.

Why it prints an origin and a scale

The primary display is 3840 by 2160 pixels. A full-size capture is more than a vision model needs and slower to read, so the script downscales to 1280 on the longest side by default. Printing the source rectangle and the scale with every capture keeps the coordinate conversion mechanical: origin plus image pixel times scale equals screen pixel. The origin matters because fullscreen captures one display, and the second display starts at x equals 3840. The prelude already works in physical screen pixels with per-monitor DPI awareness, so no second conversion is hidden anywhere. This is the one idea borrowed from the cua survey: coordinates in screenshot space, scale returned.

Why custom takes a rectangle

A small rectangle comes back at full resolution, which is a close look at a small area. That is what Anthropic's computer-use toolset exposes as its zoom tool. ACU gets zoom for free from the same script.

Why app renders the window instead of copying the screen

The window draws itself into the image, so a covered window still shows its own content and the foreground never changes. A screenshot that stole focus would undo the restore rules the prelude works to keep. The image is cropped to the visible frame, without the invisible resize border.

How it was built

An AutoHotkey script that captures through GDI+ with DllCall, so the core stays AutoHotkey, run through the same launcher as everything else. The launcher gained argument forwarding after a double dash so the agent passes the action and options on the command line. One trap found on the way: AutoHotkey loads and frees a DLL named inline on every call, which breaks GDI+ between calls. Pinning the library for the duration of the save fixed a hard crash.

What it is not

It does not find buttons; that is the accessibility tree's job in milestone 2. It does not replace waiting for a window to appear as the way to check an action; a screenshot is the check when nothing else can tell. And it is not a server or a daemon. It is one more script the agent runs.

Measured: clicks while the cursor keeps moving

Two hundred clicks per run at a 24 by 24 pixel button, one launcher process per click, while a second script moved the cursor to random points on the primary monitor.

About 99 percent in both modes, with no launcher failures. The difference between the modes is noise at this sample size, which confirms the decision to optimize for short scripts rather than for injection mode. Two surprises are recorded in the README: one atomic input batch does not guarantee a Win32 button registers the click, and one cursor move per millisecond is out of reach on this input path.

Discovered along the way

  • A program launched by a script inherits the launcher's output pipe. The launcher now waits for the AutoHotkey process, not for end-of-file, with a test that pins it. Without this, opening Notepad from a script would have stalled the launcher until Notepad closed.
  • AutoHotkey honors a close request even inside a loop that never sleeps. Only a thread blocked outside AutoHotkey needs the hard kill.
  • In AutoHotkey v2 a script can define functions named like the built-in mouse functions. That is what makes hook-free takeover tracking possible.
  • Windows 11 ignores timer-resolution requests from a windowless background process. A high-resolution waitable timer works regardless.
  • AutoHotkey's DllCall loads and frees a DLL named inline on every call. GDI+ keeps state between calls and crashes when the library goes away between them. Pin it with LoadLibrary for the duration.

Recommended next step

Use the skill on one real task from another harness before building milestone 2. A single run of an agent opening an application, changing something, and reporting the result will show whether the skill's loop and script-shape rules hold up, and that is the cheapest place to iterate. Then the accessibility tree, which fills the one remaining gap: finding a control by name instead of by eye.
