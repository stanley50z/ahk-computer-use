ACU progress

The minimal Windows computer-use tool is built. An agent can find controls, see the screen, run a short AutoHotkey action chain, and verify the result. Fresh-agent exercises have proved the skill works beyond implementation tests; the latest changes cover elevated windows and Windows-scaled app captures.

Historical snapshot of main at eae5264, before the benchmark and CLI/MCP work. Implementation and validation through 2026-10-09. Issues #1–#7 were closed; no issues were open at that snapshot.

Where we are in the grand view

We have moved from “can a scripted click coexist with the user's desktop?” to a working, project-local tool that a fresh agent can use from the skill alone. Both original milestones are delivered: reliable script execution and screenshots first, then controls by name through UI Automation.

The strongest evidence is a fresh Pi agent opening Notepad++, creating a separate document, saving exact bytes, and closing its application without editing a restored user document. A separate launcher exercise drove an elevated Notepad++ successfully. Mixed-DPI testing exposed a real screenshot defect, which is now fixed.

The core is complete; broad application coverage is not established. We have evidence from Calculator, editor/file-dialog tasks, stand-in test windows, and selected browser-tree measurements. We have not proved arbitrary long tasks, every application, or interruption-free concurrent use.

The working loop

Look

Find what the window publishes

Tree by name, id, or path first choice
Display, app, or rectangle PNG visual fallback

Act

Run one predictable action chain

Invoke, set value, toggle, select semantic actions
Click, type, drive windows UI Access

Check

Observe the user's postcondition

Read state, title, or saved bytes poll if needed
Look again when state is unclear not just exit 0

A successful invocation or launcher verdict means the script ran, not that the application did what the user wanted. Verification stays inside the agent's loop.

How the pieces fit

The agent writes a plain .ahk file and runs python acu/run.py script.ahk. There is no ACU daemon and no ACU process stays running between scripts.

1. ValidateThe plain AutoHotkey build loads without running, capturing syntax errors and warnings.
2. RunShellExecute starts the signed UI Access build; the injected prelude sets defaults and redirects output to a file.
3. FinishThe prelude conditionally restores entry state. The launcher prints output and a verdict, then records the run.

A watchdog requests close at 30 seconds by default, then kills after one second if necessary. Restore runs on normal exit, runtime errors, and a cooperative timeout close; a forced kill cannot run an exit handler.

Design decisions we made and tested

“Tested” below means the stated behavior has evidence, not that the decision is universally optimal. Some are deliberate constraints or accepted tradeoffs.

One script per action chain; no serverUse the agent's existing shell and file writer. Predictable intermediate steps do not need a model round trip each.Calculator and Save As exercises completed through scripts. This proves the interface is usable, not that a daemon could never help. Scripts share focus and cursor, so the skill requires sequential runs.
Short scripts over injection atomicityDo not suspend the user's hotkeys to recover SendInput. Remove mouse delays and minimize desktop occupancy instead.The jiggle test measured about 99% hits in both SendInput and SendEvent fallback. Neither mode guarantees every click registers. Numbers below.
Inject a prelude, not copied boilerplateCentralize coordinate mode, DPI, output, errors and restore so agent scripts cannot drift from a template.Settings checks, both-monitor click tests, syntax/runtime error tests, and plain fresh-agent scripts. Reserved names and warning collisions were found and documented or fixed.
Conditional restore, without hooksRestore at the end of the chain, not after each click. Compare actual cursor position and clicked processes; hooks would affect other AHK scripts.Restore, takeover, unrelated foreground, keep-foreground and timeout-close scenarios. Earlier intermittent failures were explained by the user's mouse use; hands-off checks passed twice with no code changes.
Keep-foreground is an explicit opt-outDefault restore should not prevent a task from leaving an application showing or transient UI open for the next look.The first live task exposed the need; AcuKeepForeground() was added and a regression checks that the cursor still restores. This revises the brainstorm's “no opt-out yet” decision.
Named controls before coordinatesInvoke or set a value without pointer input; then use element bounds; use screenshots when the tree cannot identify the target.Calculator 6 × 7 = 42 by Invoke and state readback; named button/edit/check-box tests; Notepad++ save with no coordinate clicks. A tree can still be empty or nameless.
Vendor UIA-v2; paths use control viewReuse pure-AHK MIT bindings rather than write COM bindings. Include them in every script. Keep one marked patch only.Raw-view numbering was tried and failed on Calculator. Control-view paths round-trip; single-segment paths needed one library patch. Inclusion costs about 30 ms per script.
Full tree values; narrow the dump with filtersThe user chose to expose everything the window publishes, including document text, rather than suppress or shorten values.Issue #7 added name/type filters, explicit max/depth truncation, selected state and writable-value flags. A 100-character Document value is checked uncut. This is a visibility decision, not a privacy filter.
Screenshots report physical source and scaleCapture one display, window or rectangle; keep the image-to-click conversion explicit instead of hiding a fixed canvas transform.Monitor origins, image dimensions, downscaling, custom rectangles and second-monitor clicks. At 200%/100% mixed DPI, tree bounds and a tree-center File-menu click landed correctly.
Render app captures without changing focusA covered window should show its own content. Its native rendering size must be scaled to its physical on-screen size.Covered-window capture preserves foreground. Mixed-DPI testing found cropped, oversized app images. A DPI-ratio shortcut was rejected; capture now reads dimensions in the window's own DPI context. A regression compares app pixels with the same screen rectangle.
UI Access, not administrator executionReach elevated windows without elevating the script or its child programs, prompting per run, or weakening UAC.Ordinary execution saw no elevated controls and silently dropped input. With UI Access, elevated Notepad++ exposed 67 elements; typing, click, undo and close worked through the launcher. UAC consent remains unreachable.
Wait for the script process; persist failuresA child application must not keep the launcher waiting. Close before kill permits restore. Log hashes, not script text.Child-process lifetime, cooperative timeout, forced kill, run-log and crash-report regressions. UI Access changed output from a pipe to a file and needed an allowance for the timeout's close message; those contracts were retained.
Project-local skill and opt-in desktop checksDo not change unrelated agent sessions or repeatedly take over the user's desktop during development.Discovery was verified in four harnesses; installer checks cover local links and removal. Default pytest excludes all AHK/desktop cases even when their files are selected. Live editor tasks use existing Notepad++ or Markpad, not Windows Notepad.

Measured: clicks while the cursor keeps moving

200 clicks per run at a 24 × 24 pixel button, one launcher process per click, while a second script moved the cursor to random points. Windows 11, AutoHotkey 2.0.22, primary display 3840 × 2160 at 200%.

No launcher failures; mean script time was 100–138 ms per click including process start. The results support short, no-delay scripts rather than disrupting the user's other AHK scripts. They do not promise safe concurrent typing or 100% click delivery. The rig achieved roughly one injected move per 2.5 ms, not the initially hoped-for 1 ms.

What remains limited, rather than unfinished

Accepted boundaries

  • The desktop is shared. Only one agent script should use cursor/focus at a time; short scripts reduce interruption, not eliminate it.
  • Hook-free takeover detects a cursor mismatch, not keyboard-only intervention or all direct Send "{Click}" input. Moving away and exactly back is also undetected.
  • UI Access reaches elevated windows, not the UAC consent desktop. The signed binary must remain under Program Files.
  • Canvas apps, games and unnamed controls may need screenshot coordinates. App rendering is application-dependent; minimized app capture is an error.
  • Complete tree values and failure output can contain sensitive text. Script text is not logged; default screenshots retain only the newest 30.

Questions for future use

  • Application breadth: do spreadsheet, settings, or longer cross-application tasks expose a gap in the skill?
  • Large-tree cost: the full subtree is fetched before output limits. A Chrome tree took about 0.8 s; optimize only if actual tasks justify it.
  • Shared-desktop ergonomics: does real use reveal an important missed takeover case that warrants optional hooks?
  • Distribution: the skill stays project-local during development. Global availability or an MCP front end needs a new requirement, not automatic expansion.

Recommended direction

Keep the architecture small and let another real task supply the next requirement. The useful next validation is one fresh-agent exercise in a different application, with a bounded result, ownership rules and explicit permission for that desktop run. A read-only review of eae5264 is an alternative if implementation confidence matters more than application breadth.

No remaining defect or feature from the handoff is currently open. Mixed DPI, elevated input, save polling and the restore investigation are no longer pending. There is no reason to add a server, custom action protocol or more routine desktop tests just to make a next milestone.

Default python -m pytest -q runs skill/installer checks without AutoHotkey. Run only focused checks relevant to a change; desktop checks require approval for the specific run and --desktop. The full suite is deliberate idle-desktop validation, not a routine completion gate. No desktop checks were rerun to update this report.
